## 3. 확장 시나리오 — 개발 예정

### S5: 목표 시간과 필수 내용을 준비한다

1. “발표 자료 준비”에서 대본을 붙여넣는다.
2. 최소 4분 30초·최대 5분을 입력한다. 이 값은 테스트 예시이며 사용자 과제 조건이 아니다.
3. 필수 전달 항목과 근거 문장을 입력한다.
4. “원본 저장”을 누른다.

기대 결과: 원본 버전·조건·필수 항목이 연결되어 저장된다. 잘못된 범위에서는 저장되지 않고 이유가 표시된다. 관련: F7–F8 / AC-07–08 / UI-05.

### S6: 초과한 발표 대본을 수정한다

1. 저장한 대본으로 전체 연습을 마친다.
2. “수정안 검토”를 연다.
3. 중복 설명 축약안의 원문·제안·근거·필수 내용 검사를 읽는다.
4. 채택할 항목의 “적용”을 누른다.

기대 결과: 원본은 보존되고 새 버전이 생성된다. 보호할 수치·조건을 바꾼 제안은 변경 의심으로 표시되고 조용히 자동 적용되지 않는다. 관련: F9–F10 / AC-09–10 / UI-06.

### S7: 시간이 부족한 발표를 근거에 따라 보완한다

1. 미달 결과에서 “수정안 검토”를 연다.
2. 사용자가 실제로 제공한 예시·근거가 있는 구간의 보완안을 확인한다.
3. 자료가 부족한 항목의 추가 근거를 입력하거나 보완을 보류한다.
4. 확인한 제안을 새 버전으로 저장한다.

기대 결과: 임의의 성과·통계·경험을 추가하지 않는다. 미달을 해결하기 위해 무의미한 문장을 채우지 않으며 내용이 부족하면 그 상태를 남긴다. 관련: F9–F10 / AC-09–10 / UI-06.

### S8: 고친 구간과 전체 발표를 다시 확인한다

1. “수정 항목 재점검”에서 항목을 선택한다.
2. “이 구간 연습”으로 재연습한다.
3. 이전과 이번의 발화 근거·실제 시간·필수 내용 상태를 확인한다.
4. “전체 발표 확인”으로 전체 연습을 수행한다.
5. 결과를 내보낸다.

기대 결과: 부분 결과와 전체 실측이 구분된다. 같은 기준의 항목은 해결/미해결/판단 불가로 표시되고, 조건 변경은 별도 안내된다. 관련: F11–F12 / AC-11–12 / UI-07–08.

### S9: 관찰을 확인하고 당시 상황을 설명한다

1. 결과의 반복 후보를 재생하고 관찰을 확인하거나 교정한다.
2. “상황 확인”에서 당시 어려움을 설명한다. 긴장했다는 답변이 있으면 걱정된 조건을 후속 질문으로 확인한다.
3. 서비스가 요약한 본인 설명을 확인한다. 모르겠음·건너뛰기도 선택 가능하다.

기대 결과: 관찰·본인 설명·추정을 구분한다. 질문은 기본 최대 3개이며 긴장이 기본 원인으로 선택되지 않는다. 오탐·문제 아님이면 해당 지적을 닫을 수 있고 연습은 계속된다. 관련: F13 / AC-13 / UI-09.

### S10: 반복이 생기는 조건을 바꾸어 시험한다

1. “연습 조건 시험”에서 원문 기반 핵심어 메모 등 제안을 확인한다. 이 예시는 검증된 효과가 아니다.
2. 한 가지 조치를 선택하고 적용 미리보기를 확인한다.
3. 기준과 가능한 한 같은 구간을 다시 연습한다.
4. 군말 횟수·분당 빈도, 내용·시간·선택적 부담과 바뀐 조건을 함께 확인한다.
5. 도움이 없으면 되돌리거나 다른 방법을 선택한다. 단서 사용이 불가능한 실제 발표에 대비하는 전체 연습도 별도로 수행한다.

기대 결과: 원인을 몰라도 조치를 선택할 수 있다. 횟수 감소만으로 성공이나 긴장 극복을 선언하지 않는다. 연습 자체·변경 조건·전사 품질의 영향을 구분해 표시한다. 관련: F14·F11 / AC-14·11 / UI-10·07.

## 4. 공통 문구 규칙

- 현재 측정: “실제 연습 시간”. 계산: “예상 시간 — 계산 근거 …”. 인식 실패: “측정하지 못함 — 이유 …”.
- AI 제안: “수정 제안”. 자동 적용 전 사용자 선택. 결과가 불확실하면 “확인 필요”.
- 개인정보: 로컬 저장, 브라우저 음성 인식, 외부 AI 텍스트 전송을 각각 설명한다.
- 긴 침묵·반복: “다시 확인할 구간”. 무조건 나쁜 발표로 판단하지 않는다.
- 원인 질문: “긴장해서 그렇죠?” 대신 당시 어려움을 먼저 묻는다. “사용자가 설명한 상황”과 “이번 조건에서의 변화”로 표시하고 원인 확정·극복 완료로 쓰지 않는다.
- 개선 판정: 시간만 짧아졌다는 이유로 성공이라고 쓰지 않는다. 필수 내용·동일 조건·전체 실측을 함께 본다.

## 5. 웹 화면 검증 기준

주 사용 화면은 PC·노트북이며 최소 검증 크기는 1366×768로 계획한다. 확대·키보드·작은 창에서도 입력과 핵심 버튼에 접근할 수 있어야 한다. 휴대전화 접속은 레이아웃 보조 대응이며 모바일 앱 개발 범위를 뜻하지 않는다. 실제 지원 브라우저와 화면 시험 결과는 검증 후 기록한다.

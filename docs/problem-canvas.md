# 문제 정의 캔버스 — 앞면·뒷면

기준일: 2026-10-29. 각 칸에 옮길 수 있는 전체 문구다. 원자료는 [problem.yaml](problem.yaml), 근거 구분은 [decisions.md](decisions.md)를 따른다.

## 앞면

### 한 문장 문제 정의

발표를 준비하는 대학생은 혼자 연습할 때 시간 초과·미달과 고칠 구간을 점검하고, 수정한 내용이 실제로 나아졌는지 확인하기 위해 녹음·영상을 반복해서 살펴보며 시간과 노력을 들인다.

### ① 상황

수업이나 팀 프로젝트 발표를 앞두고 집이나 빈 강의실에서 혼자 연습할 때 발생한다. 내용 전달에 집중하거나 긴장하면 말하기 속도와 시간을 함께 관리하기 어렵고, 제한 시간을 초과하거나 지정된 시간을 채우지 못할 수 있다. 연습 후에는 직접 녹음하고 웹캠으로 녹화한 내용을 다시 보며 고칠 부분을 점검한다.

### ② 고객

수업이나 팀 프로젝트에서 발표를 맡은 대학생이다. 특히 발표 경험이 충분하지 않고, 다른 사람의 도움을 받기 어려운 상황에서 정해진 시간에 맞춰 혼자 연습하고 개선해야 하는 사람을 핵심 대상으로 한다.

### ③ 근본 문제

발표하면서 내용·속도·시간을 동시에 점검하기 어렵고, 연습 후에는 녹음·영상에서 검토할 부분을 찾고 수정한 결과를 다시 확인하는 일을 직접 해야 한다. 어떤 구간을 어떻게 바꿀지 판단하고 재연습에서 확인하는 과정에 추가 노력이 든다.

### ④ 영향

**그때 한 말·기분:** “되게 시간이 오래 걸렸어.” 직접 녹음·녹화하고 다시 확인하는 과정에서 시간 부담을 느꼈다.

**시간·기회:** 본인은 대사 암기와 직접 녹음·웹캠 녹화 및 반복 점검 등을 포함한 발표 준비 전반에 약 10시간이 들었다고 기억한다. 정확히 측정한 시간이 아니며 영상 검토에만 든 시간이나 전부 자동화로 줄일 수 있는 시간을 뜻하지 않는다. 시간 초과와 미달을 모두 경험했지만 정확한 종료 시각과 실제 감점 여부는 확인되지 않았다.

### ⑤ 현재 대안 / ⑥ 대안의 단점

| 대안 | 현재 사용하는 방법 | 남는 불편·확인 범위 |
| --- | --- | --- |
| A1 | 직접 녹음하고 웹캠으로 녹화한 뒤 다시 재생하며 점검한다. | 검토할 구간을 직접 찾고 수정 전후의 차이를 확인하는 데 시간이 든다. 본인의 경험으로 확인한 부담이다. |
| A2 | 타이머·스톱워치로 전체 시간을 재고 대사를 외우며 대본 분량과 속도를 조절한다. | 총 시간은 알 수 있지만 어떤 내용을 줄이거나 보완할지와 수정 효과는 직접 판단해야 한다. |
| A3 | PT샌드백으로 장표별 시간 설정·대본 편집·발표 연습을 한다. | 직접 확인한 무료 경로에서 목표 시간을 1분에서 2분으로 바꾸고 균등 배분해도 대본은 그대로였다. AI·유료 기능 전체의 자동 수정 가능 여부는 미확인이다. |
| A4 | Talkli로 속도·반복 등을 점검하고 녹음 회차를 비교한다. | 회차 비교는 이미 공식 기능이다. 목표 시간 기반 자동 대본 수정의 제공 여부와 앱 내부 품질은 이번 조사에서 확인하지 못했다. |
| A5 | SayNow의 말하기 훈련·성장 기록과 웹 피치·시간 도구를 사용한다. | 웹 피치 도구에 긴 가상 내용을 입력했을 때 30초 버전이 예상 49초가 되어 사용자가 답변을 줄이라고 안내했다. 이 결과를 모바일 앱 전체의 한계로 확대하지 않는다. |

A1–A2는 본인 경험에 기반한 대안이다. A3–A5는 조사한 서비스이며 본인이 실제로 모두 사용했다고 기록하지 않는다.

## 뒷면

### 1. 관찰 정황

**P1 — 대상:** 수업이나 팀 프로젝트 발표를 준비하는 대학생 본인이다. 혼자 연습하면서 발표 내용, 말하기 속도, 제한 시간을 함께 관리해야 했다.

**E1 — 언제:** 대학교 응용 프로젝트 발표를 준비하고 실제 발표할 때. 정해진 발표 시간에 맞춰 내용을 전달해야 했다.

**E1 — 무슨 일:** 긴장하면 말이 빨라지고 내용 전달에 집중하느라 경과 시간과 남은 시간을 함께 확인하기 어려웠다. 실제 발표에서 제한 시간을 초과한 적도, 지정된 시간을 채우지 못한 적도 있었다.
연습할 때 직접 녹음하고 웹캠으로 녹화한 뒤 다시 재생해 보며 점검했다. 이 과정이 오래 걸렸고 대사 암기 등 준비 전반에 대략 10시간이 들었다고 기억한다.

**E1 — 어떻게 버텼나:** 대사를 외우고 타이머·스톱워치로 시간을 재며 반복 연습했다. 직접 녹음하고 웹캠으로 녹화한 뒤 재생하며 점검했다.

**E1 — 기분·말:** “되게 시간이 오래 걸렸어.”

**출처:** 사용자가 제공한 본인 발표 준비·발표 경험 대화. 준비 시간은 회고이며 정확한 종료 시간·감점·활동별 시간은 미확인. 기존 문서의 10~11분 규칙과 10분 30초 목표는 docs/decisions.md에 보존하고 재확인 대상으로 구분했다.

**P2·E2:** 추가 사례 없음. 비워둔다.

### 2. 5 Whys

혼자 발표를 연습한 뒤 점검하고 수정 효과를 확인하는 데 왜 시간과 노력이 드는가?

1. 녹음·웹캠 영상을 직접 다시 재생하며 고칠 부분을 점검하기 때문이다. (본인 경험)
2. 전체 시간과 녹음만으로 어느 내용을 어떻게 바꿀지 바로 정하기 어렵기 때문이다. (?)
3. 구간의 시간 사용과 전달해야 할 내용을 함께 판단해야 하기 때문이다. (?)
4. 수정 전후 대본과 실제 발화를 연결해 다시 확인해야 하기 때문이다. (?)
5. 반복 연습과 수정 효과 확인이 연결되지 않으면 같은 점검을 수동으로 되풀이하기 때문이다. (?)

**근본 문제 — 앞면 ③에 반영:** 발표하면서 내용·속도·시간을 동시에 점검하기 어렵고, 연습 후에는 녹음·영상에서 검토할 부분을 찾고 수정한 결과를 다시 확인하는 일을 직접 해야 한다. 어떤 구간을 어떻게 바꿀지 판단하고 재연습에서 확인하는 과정에 추가 노력이 든다.

`(?)`는 추가 확인이 필요한 원인이다. 제품 설계에 필요하다고 해서 사용자 경험으로 확인된 원인으로 바꾸지 않는다.

### 4. 통찰 / INSIGHT

**① 관찰 — claim:** 발표 연습 자체뿐 아니라 녹음·영상에서 점검할 부분을 찾고 수정 후 다시 확인하는 과정에도 부담이 있었다.

**② 근거 — evidence:** 본인은 직접 녹음·웹캠 녹화 후 다시 보았고 그 과정에 시간이 오래 걸렸다고 말했다. 대사 암기 등을 포함한 준비 전반은 약 10시간으로 기억하며 시간 초과·미달을 경험했다. 한 사람의 회고다.

**③ 제작 결정 — design decision:** 설치 없는 PC·노트북 웹으로 개발한다. 기존 시간·기록·검토 기능을 유지하고 개인 실측 기반 대본 수정, 필수 내용 보존 검사, 수정 항목별 재점검을 추가 설계한다. 신규 기능은 미구현으로 구분한다. 웹캠은 선택이며 표정·자세·감정 평가와 설치형 앱은 범위에서 제외한다.

### 앞면·뒷면 일치 점검

- 시간 초과와 미달을 모두 다룬다.
- 10시간을 전체 준비 시간에 대한 회고로 표현한다.
- 고객·근본 문제·영향·대안·해법의 연결을 유지한다.
- 경쟁사 미확인 기능은 없다고 단정하지 않는다.
- 웹 서비스로 통일하고 현재 기능과 개발 예정 기능을 구분한다.

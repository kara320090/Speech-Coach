# 자체 실행 AI 설계·공개 프로젝트 참고 분석

기준일 2026-10-29. 사용자 선택: **공개 모델을 직접 실행하되 초기에는 추가 학습 없이 개발**. 이 문서는 전체 설계다. 이후 모델 설치·추론·첫 구현을 수행했고 [구현 범위](local-ai-implementation.md)에 실제 결과를 기록했다. 추가 학습은 하지 않았다. 새 개발은 브랜치·PR로 제출하고 main에 직접 push하지 않는다.

## 1. 개발의 의미와 범위

공개 모델의 가중치를 가져와 개발자 PC 또는 직접 운영하는 서버에서 추론한다. 팀이 만드는 부분은 대본·근거 연결, 질문 상태 관리, 쉬운 표현 제안, 응답 검증, 재설명·재연습 비교와 웹 화면이다. 처음부터 모델을 훈련하거나 LoRA·파인튜닝을 수행하는 계획은 없다. 발표 자료를 요청 문맥으로 제공하는 것은 학습이 아니다.

서비스 이용자는 웹브라우저로 사용한다. 운영자에게 필요한 모델·실행기 설치를 사용자용 앱 개발과 혼동하지 않는다. 기존 Node 22 서버와 바닐라 프론트 구조를 유지하고 AI 추론은 별도 프로세스로 분리한다. 원격 유료 AI 서비스, 외부 AI Gateway, 클라우드 모델 자동 대체를 새 흐름에 사용하지 않는다.

## 3. 자료와 모델의 역할

1. 사용자가 대본과 근거 자료를 각각 붙여넣는다. 문단·개념·버전에 ID를 부여한다. AI 생성 대본만 있으면 그 사실을 표시한다.
2. 모델이 낯설 수 있는 표현을 원문 인용과 함께 후보로 낸다. 사용자가 아는 용어는 제외하거나 직접 표시할 수 있다.
3. 사용자가 선택한 개념을 자기 말로 설명한다. 모델은 답변의 실제 문구와 자료 근거를 비교해 확인된 부분·보완할 부분을 제시한다. 군말·표정·답변 길이는 이해 판정 입력에서 제외한다.
4. 모델이 짧은 문장·익숙한 표현·필요한 용어 풀이를 제안한다. 수치·단위·조건·부정·한계·필수 항목의 변화는 코드 검사와 사람 확인으로 보완한다.
5. 자료로 답할 수 있는 예상 질문을 제시하고 사용자가 먼저 답한다. 모르면 쉬운 설명을 받을 수 있다. 근거가 없는 질문은 추가 자료 필요로 표시한다.
6. 원본·제안·선택 버전·답변·도움 제공 여부를 보존한다. 같은 개념의 표현을 바꾼 질문과 전체 발표 연습을 통해 재확인한다.

자료에 실제 존재하는 인용인지는 코드로 확인할 수 있지만, 인용이 답변을 논리적으로 뒷받침하는지까지 문자열 검사로 보장할 수 없다. 따라서 자동 비교 결과는 사용자 검토 상태와 분리하고 불확실하면 판단 불가로 둔다. 외부 사실 검증과 임상·정서 진단은 수행하지 않는다.

## 4. 구성과 전송 경계

```text
웹 화면 / IndexedDB 원본·기록
       │ 사용자가 분석을 요청한 최소 텍스트·답변
       ▼
Node 22 서버: 크기·버전·동시 요청·취소·출력 검증
       │ 내부 연결 (개발 중 기본 127.0.0.1)
       ▼
llama-server + 고정 공개 모델

후속: 사용자가 선택한 음성 조각 → 자체 전사 프로세스 → 전사 검토
영상·얼굴 분석은 기존처럼 브라우저에서만 처리
```

여기서 HTTP 경로는 서비스 내부 통신이며 외부 AI 제공자 API 계약·키를 쓰는 방식이 아니다. 브라우저에서 우리 서버로 텍스트를 보내는 것 자체는 전송이므로 “기기를 전혀 떠나지 않음”으로 안내하면 안 된다. 개발자 PC에서 모두 실행할 때와 직접 운영 서버를 사용하는 배포 모드를 구분해 처리 위치를 표시한다.

기존 Render 구성만으로 개발자 PC의 `127.0.0.1` 모델에 접근할 수 없다. 자체 AI 서비스 배포에는 추론 프로세스가 실행될 운영 장비와 안전한 내부 연결이 필요하다. 공개 브라우저에 추론 서버 주소·관리 포트를 직접 노출하지 않는다. 실제 제공 주소·장비·동시 사용자 수는 아직 미정이다.

모델·실행기 최초 다운로드는 네트워크와 디스크를 사용한다. 이후 런타임에서는 준비된 파일만 사용하고 자동 다운로드·외부 폴백을 금지한다. 모델 파일은 public·Git에 두지 않는다. 장비의 RAM·GPU 메모리·디스크·응답 지연을 측정한 뒤 모델·양자화·문맥 한도를 확정한다. 후보 선정을 실제 실행 가능성·품질 보증으로 표현하지 않는다.

## 7. 개발 지시서에 포함할 규칙

- 먼저 최신 README·problem.yaml·요구사항·본 문서를 읽고 구현과 계획을 구분한다. 기존 F1–F16 ID를 재사용하지 않는다.
- 모델 호출 어댑터와 프롬프트·형식 검증을 분리한다. 입력 문서의 지시문은 데이터로 다루고 도구 실행·외부 URL 방문을 수행하지 않는다.
- 개념 단위의 필요한 문맥부터 처리한다. 긴 입력을 말없이 자르지 않고 범위 선택·추가 처리를 안내한다. 초기 벡터 DB·검색 인프라는 필수가 아니다.
- JSON 스키마·길이·허용 상태·문서 버전·실제 인용·수치·단위를 검사한다. 실패하면 제안을 적용하지 않고 재시도/직접 수정으로 복구한다.
- 외부 제공자 기본 URL·키·폴백을 넣지 않는다. 입력 본문·답변·음성·모델 원문 출력을 로그에 남기지 않는다. 내부 서버 주소는 운영자 설정만 허용한다.
- 모델 정지·메모리 부족·지연·출력 오류를 시험한다. 작은 입력·출력·문맥 한도, 동시 추론 1개부터 시작하고 실제 지연 측정 후 확장한다.
- 프론트 app.js·styles.css·index.html 변경은 최소화한다. UI를 별도 모듈로 추가하고 기존 버튼명·S1–S4를 바꾸지 않는다.
- 주최 측 YAML 흐름을 계획 화면으로 늘리지 않는다. 장치·모델 의존 시험은 별도 설정에 두고 기본 CI는 모델 없이 끝난다.
- 기능별 단위·브라우저 검사와 실제 모델 품질 검사를 구분한다. 가짜 모델 출력 통과를 한국어 품질 검증으로 보고하지 않는다.
- 새 브랜치·PR로 제출하고 확인/미확인·모델 버전·실행 장비·지연·오류를 progress에 기록한다.
